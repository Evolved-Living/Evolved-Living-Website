# SITE_ARCHITECTURE_SPEC.md

## Purpose

This document defines the formal architecture and repository structure for the Evolved Living website.

The goals of this architecture are:

- Simplicity
- Maintainability
- Consistency
- Mobile scalability
- Minimal JavaScript dependency
- Easy content editing
- Predictable rendering behavior

This structure is intended for a static website hosted via GitHub Pages.

---

# 2. Core Architectural Model

The website is built around a **content block system**.

Each page consists of a vertical stack of content blocks.

Each content block:
- Spans the full width of the viewport
- Contains its own internal layout
- Is mobile-responsive
- May contain nested sub-blocks

Pages are generated by:
1. Loading a page-specific JSON file
2. Parsing the JSON content
3. Rendering the content into predefined content block templates

---

# 3. CSS Architecture

The CSS system is divided into FIVE files.

---

## 3.1 `theme-main.css`

Purpose:
- Defines the visual identity of the website
- Defines all color variables
- Defines typography variables
- Defines spacing variables
- Defines shadows, borders, and transitions

This file contains:
- CSS variables only
- Site-wide visual theme definitions

This file SHOULD NOT contain:
- Layout definitions
- Content block structure
- Page-specific rules

---

## 3.2 `global.css`

Purpose:
- Defines layout for global elements

This file contains:
- Header/footer shell
- page container sizing
- site-wide wrappers

---

## 3.3 `utilities.css`

Purpose:
- Defines reusable utility classes

This file contains:
- helper classes
- spacing utilities
- visibility utilities

---

## 3.4 `components.css`

Purpose:
- Defines reusable component wrappers
- Defines panel, card, and media patterns
- Standardizes shared section layers across the site

This file contains:
- section wrapper classes
- panel/card components
- grid and action helpers
- banner and media containers

---

## 3.5 `content-blocks.css`

Purpose:
- Serves as the compile point for page blocks
- Assembles reusable components into final block layouts
- Defines block-specific composition rules
- Supports responsive content layouts

This file contains:
- hero, services, split-content, and banner blocks
- process/testimonial/contact compositions
- block responsive adjustments
- block-level presentation details

---

# 4. Content Block System

## 4.1 Content Blocks

A content block is the primary layout unit of the website.

Rules:
- Full viewport width
- Vertically stacked
- Self-contained
- Responsive by default

Examples:
- Hero block
- Services block
- Image showcase block
- Contact CTA block
- Testimonial block

---

## 4.2 Sub-Blocks

Sub-blocks exist inside content blocks.

Purpose:
- Group related content
- Allow flexible scaling
- Improve mobile responsiveness

Sub-blocks may contain:
- Text
- Images
- Buttons
- Links
- Cards
- Lists

When viewport width decreases:
- Sub-blocks may wrap
- Sub-blocks may stack vertically
- Layout must remain readable

---

# 5. HTML Architecture

Each HTML file is intentionally minimal.

The primary difference between pages is:
- Which JSON content file is loaded

Example:

```html
<body data-content-source="content/index.json">
```

The HTML files should:
- Load CSS
- Load JavaScript
- Define a root content container
- Remain structurally simple

HTML files SHOULD NOT:
- Contain large amounts of hardcoded content
- Define layout variations
- Contain page-specific styling

---

# 6. Content Architecture

The `/content/` directory contains:

- Page JSON files
- Related static assets

Each page has a corresponding JSON file.

Examples:

```text
content/index.json
content/services.json
content/contact.json
```

---

## 6.1 JSON Responsibilities

JSON defines:
- Content block order
- Block type
- Text content
- Image references
- Links
- Button labels
- Sub-block content

JSON SHOULD NOT define:
- Raw CSS
- Layout rules
- Arbitrary HTML

---

## 6.2 Example JSON Structure

```json
{
  "blocks": [
    {
      "type": "hero",
      "title": "Built Around Your Life",
      "subtitle": "Custom homes designed for modern living.",
      "buttons": [
        {
          "label": "View Services",
          "href": "services.html"
        }
      ]
    },
    {
      "type": "services-grid",
      "items": [
        {
          "title": "Custom Homes",
          "description": "High-quality residential construction."
        }
      ]
    }
  ]
}
```

---

## 6.3 Global Content Architecture

`global.json` contains:
- navigation
- company information
- footer content
- shared CTAs
- shared contact information

The renderer loads `global.json` before page JSON and makes it available to all blocks.

---

# 7. JavaScript Architecture

The JavaScript layer handles:

1. Loading JSON content
2. Mapping JSON to content block templates
3. Rendering blocks into the page
4. Minor UI enhancements

JavaScript is responsible for translation between:

```text
JSON content → Content block template → Rendered page
```

---

## 7.1 `content-loader.js`

Responsibilities:
- Detect current page content source
- Load the correct JSON file
- Pass parsed data to renderer

---

## 7.2 `content-renderer.js`

Responsibilities:
- Select appropriate content block templates
- Populate template content
- Render blocks in sequence
- Handle nested sub-blocks

---

## 7.3 `utilities.js`

Responsibilities:
- Shared helper functions
- Generic utilities
- Non-rendering helper logic

---

# 8. Rendering Model

Rendering behavior is sequential.

The renderer:
1. Reads the `blocks` array
2. Selects the matching block template
3. Renders blocks in order
4. Appends each block to the page container

Because content blocks are full-width sections:
- The page naturally stacks vertically
- Layout consistency is easier to maintain
- New sections can be added without modifying page structure

---

# 9. Responsive Design Requirements

All blocks and sub-blocks MUST:

- Scale cleanly on mobile and desktop
- Avoid horizontal scrolling
- Maintain readable spacing
- Reflow content predictably

Preferred layout behavior:
- Desktop → horizontal grouping
- Mobile → vertical stacking

---

# 10. Loading Behavior

HTML contains:
- loading indicator
- root render container
- noscript message

Rendering sequence:
1. Show loading state
2. Load global.json
3. Load page JSON
4. Render blocks
5. Hide loader
6. Reveal page

This prevents:
- white flashes
- confusing blank states

---

# 11. Naming Conventions

Naming must prioritize clarity.

Preferred:
- `hero-block`
- `services-grid`
- `contact-cta`

Avoid:
- Abbreviations
- Generic names like `section1`
- Clever or abstract naming

- Make layout reusable
- Improve maintainability

- Reduce repeated page structure
